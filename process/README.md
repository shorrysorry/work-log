# 개발 프로세스 — 팀이 일하는 방식을 고치다

| 항목 | 내용 |
|---|---|
| 축 | 개발 프로세스 |
| 기간 | 2022-09 ~ 현재 (프로세스 개선 제안은 2026-08 ~ ) |
| 역할 | PRD 구조 개선 **제안·결정 기록·체계 구현** · 구현 전 스펙 리뷰 **주도** · 코드 리뷰어 · 통합·릴리즈 담당 |
| 규모 | PRD 분석 52건(표본 10건) · 구조 결정 15건 · 스펙 리뷰 결정 요청 39건 · 코드 리뷰·승인 80건 · 통합 merge 156회 · 릴리즈 담당 56건 |

## 한 줄 요약

프론트엔드 개발자가 **구현을 시작하고 완료를 판정하는 데 필요한 정보가 기획 문서에 흩어져 있다**는 문제를 실제 문서 데이터로 보여주고,
PRD 구조를 바꾸는 결정을 팀과 합의한 뒤, 그 구조로 작성·검증하는 체계까지 만들었습니다.

---

## 1. PRD 구조 개선 — 제안에서 체계 구현까지 (2026-08 ~ 09)

### 문제를 데이터로 정의 (2026-08)

기획 문서(PRD) 데이터베이스 전체 **52건**의 속성·상태를 분석하고, 진행 단계가 다른 실제 문서 **10건**을 표본으로 프론트엔드 구현 관점에서 검토했습니다.

찾은 문제 (요약)

- 문서의 순서가 구현 순서가 아니라 사후 정책 문서의 분류 체계를 따른다 → 한 시나리오를 구현하려면 여러 섹션과 디자인 파일을 왕복해야 한다.
- 화면 상태·인터랙션의 원문이 기획 문서 밖(디자인 파일)에 있다 → 로딩·빈 값·오류·권한 없음 같은 상태가 빠지기 쉽다.
- 데이터·API와 화면 동작 사이의 약속(오류 매핑, 캐시 무효화, 중복 요청 등)을 적을 고정 위치가 없다 → 착수 후 질의가 몰린다.
- 완료 조건이 설명문이라 구현·리뷰·QA가 서로 다른 단위로 검증한다.
- 대부분 "해당 없음"인 고정 섹션이 길어 실제 영향 신호를 찾기 어렵다.
- 문서 상태는 있지만 **구현 착수 가능 여부**는 드러나지 않는다.

개선 방향은 문서를 길게 만드는 것이 아니라 **"모든 변경에 공통인 구현 코어 + 해당될 때만 펼치는 조건부 모듈"**로 재구성하는 것이었고,
시나리오 단위 구현 계약, UI 상태 매트릭스, 검증 가능한 수용 기준, 착수 준비 조건(Definition of Ready)과 파일럿·측정 지표까지 담은 개선안을 냈습니다.

### 합의를 결정 기록으로 남김 (2026-08-21 ~ 26)

개선안을 바탕으로 PRD 구조에 관한 **결정 15건**을 배경·결정·이유·적용 원칙·예상 결과 형식으로 기록하고 팀 위클리에서 공유했습니다. 주요 결정:

- PRD의 최우선 독자는 프론트엔드 개발자다.
- 화면 상태·조건·인터랙션의 원문은 PRD에 두고, 디자인 파일은 시각 표현을 맡는다. 디자인 링크는 정확한 화면 단위로만 인정한다.
- 본문은 사용자 시나리오를 기본 단위로 하고, 모든 시나리오에 필수 항목과 검증 가능한 완료 조건을 둔다.
- 문서 완료와 API 계약·구현 준비 상태를 분리한다.
- 공통 영향은 체크리스트로 확인하고, 영향이 있는 영역만 상세히 쓴다.
- 각 정보의 원문은 한 곳에만 두고 다른 곳에서는 식별자로 참조한다.
- 결정이 바뀌면 지우지 않고 상태와 변경 이유를 남긴다.

### 작성·검증 체계로 구현 (2026-09)

합의한 구조를 문서 템플릿에만 두지 않고, **작성 규칙 + 구조 검증 스크립트(테스트 포함) + 단계별 점검 게이트**로 만들어 저장소에 넣었습니다.
AI 에이전트가 이 규칙으로 PRD를 작성·검증하도록 했고, 이 부분은 [AX 전환](../ax/#3-ai로-스펙-품질을-검증하는-체계-2026-09)에 정리했습니다.

이후 대형 기능 하나의 통합 PRD를 이 구조로 작성해 실제 개발에 적용했습니다.

## 2. 구현 전 스펙 리뷰 — 결정 요청을 티켓으로 (2026-11)

구현에 들어가기 전에 PRD·디자인·API 계약을 대조해, 빠지거나 서로 어긋난 부분을 **결정 요청 티켓**으로 기획·디자인·백엔드에 올렸습니다.

| 기능 | 결정 요청 | 근거 누락·충돌 | 제품 판단 필요 | 승인 차단 항목 | PRD 반영 |
|---|---|---|---|---|---|
| 신규 외부 서비스 연동 | 32 | 26 | 4 | 6 | 27 |
| 캘린더 일정 표시 개선 | 7 | 4 | 3 | 4 | 7 |

- 티켓마다 판단할 직군(기획·디자인·개발)과 승인을 막는 항목인지를 표시해, 누가 무엇을 먼저 결정해야 하는지 드러나게 했습니다.
- 결정이 나면 PRD 본문에 반영해, 구현 기준이 문서 하나로 모이게 했습니다.

## 3. 작업 문서와 구현의 동기화 (2026-10 ~ 11)

대형 기능을 개발하는 동안 **구현 중 내려진 결정, 태스크 분배, 코드 리뷰 결과**를 작업 문서에 계속 반영했습니다 (문서 커밋 94개).

## 5. 팀 운영 · 지식 공유

- 프론트엔드 내부 미팅과 **데일리 스크럼 체계**를 만들었습니다 (2026-03).
- 브라우저 확장 배포 가이드 등 팀 위키 문서를 작성했습니다.

## 일하는 방식에서 드러난 점

- **불편을 데이터로 바꾼다.** "PRD가 불편하다"가 아니라 52건을 분석해 문제를 유형화하고 개선안을 냈다.
- **합의를 기록으로 남긴다.** 결정마다 배경과 이유를 적어, 바뀌어도 왜 바뀌었는지 남게 했다.
- **규칙을 사람의 기억이 아니라 도구에 둔다.** 합의한 구조를 검증 스크립트와 게이트로 만들었다.
- **구현 전에 묻는다.** 착수 전 결정 요청으로, 구현 중 재작업이 될 질문을 앞당겼다.

## 이야기 포인트

- "팀 프로세스를 개선한 경험은?" → 데이터 분석 → 제안 → 결정 기록 → 체계 구현의 흐름
- "기획·디자인과 어떻게 협업하나요?" → 구현 전 결정 요청 티켓, 판단 주체와 차단 여부를 명시
- "리뷰나 배포에서 맡은 역할은?" → 리뷰·승인, 통합, 릴리즈 담당 수치
