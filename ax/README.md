## 한 줄 요약

팀이 쓰는 AI 개발 하네스를 **Codex에서도 돌아가게 옮기고**, 디자인 검증 게이트를 더해 **에이전트가 만든 결과를 사람이 믿고 받을 수 있는 구조**를 만들었습니다.
그 방식을 제 일상 개발에도 그대로 적용해, 2026년 하반기 제 커밋의 76%를 AI와 함께 작성했습니다.

## 1. 팀 AI 개발 하네스를 Codex로 이식 (2026-03 ~ 04)

**배경** — 팀은 Claude Code 위에서 돌아가는 공용 AI 개발 하네스를 쓰고 있었습니다.
skill·에이전트·훅을 조합해 "탐색 → 계획 → TDD 구현 → 검증 → 기록"을 단계별로 강제하는 워크플로입니다.
이 워크플로를 Codex에서도 같은 방식으로 쓸 수 있게 하는 작업을 맡았습니다.

**먼저 정한 것 — 범위와 기준**

- 같은 저장소 안에 **독립 패키지**로 두고, Claude 쪽을 기준(source of truth)으로 삼아 **매핑 문서로 동기화**한다.
- 1차 범위는 **핵심 워크플로만** — 외부 도구 연동과 팀 협업 기능은 뒤로 미뤘다.
- 결정과 수행 내역은 세션 단위로 **마이그레이션 이력 문서**에 남겨, 다음 동기화 때 같은 판단을 반복하지 않게 했다.

**한 일**

- 설치·설치 검증 스크립트, 세션 시작 점검, 워크플로 단계 상태 관리 도구를 만들었다.
- 기존 워크플로 skill **27개**를 Codex 규칙에 맞게 옮겼다 (기능 개발·핫픽스·스펙 분석·TDD·리뷰·마무리 등).
- 기준 버전이 올라갈 때마다 **동기화를 두 차례** 반영했고, 버전 확인 실패가 세션 시작을 막지 않도록 고쳤다.
- 단계 게이트와 디자인 검증 보조 도구를 Codex 쪽에도 추가했다.

## 2. 하네스 자체를 개선 (2026-04, 2026-11)

### 디자인 근거 기반 FE 흐름 게이트

에이전트의 화면 구현 결과를 **디자인 근거로 자동 검증**하는 흐름을 하네스에 넣었습니다.

- 디자인 파일에서 화면 요소 목록과 태스크 초안을 자동으로 뽑아 계획 단계에 넣었다.
- 구현·검증 단계가 그 결과를 받아 쓰도록 FE 워크플로를 바꿨다.
- 태스크 완료 시점의 훅이 **시각 검증 결과를 모아, 통과하지 못하면 완료 자체를 막게** 했다.
- 규모: 파일 28개, +1.7k 줄.

### 구현·리뷰 에이전트를 API / FE로 분리

구현 에이전트와 리뷰 에이전트를 각각 **API용·FE용으로 나누고 스택별 규약을 내장**했습니다.
워크플로 단계마다 작업 대상(API/FE)에 맞는 에이전트로 연결되도록 라우팅도 함께 바꿨습니다.

### MR 생성 skill 보강

- 권한 부족 등으로 자동 생성이 실패하면 **재시도하지 않고 수동 생성 경로를 정확히 안내**하게 했다.
- 통합 브랜치를 검증 브랜치로 올리는 모드를 추가하고, 대상 브랜치의 커밋이 섞이면 **중단**하도록 했다.
  기능을 따로따로 배포할 수 있어야 한다는 팀 브랜치 원칙을 도구가 지키게 하기 위해서다.

## 3. AI로 스펙 품질을 검증하는 체계 (2026-09)

> 프로세스 관점의 배경과 흐름은 [개발 프로세스](../process/)에 정리했습니다. 여기서는 AI가 맡은 부분만 적습니다.

PRD를 **에이전트가 작성·검증하는 skill과 규칙**을 만들었습니다.

- PRD 작성 skill과 작성 규칙, 템플릿
- 구조 검증 스크립트와 그 테스트
- **질문 게이트** — 완결성 점검, 초안 단계 결정 사항 점검
- **용어 정합성 게이트** — 도메인 용어가 문서마다 다르게 쓰이지 않는지
- **디자인 근거 검증** — PRD 서술이 실제 디자인에 근거하는지
- **PRD 간 교차 검토 skill**과 평가 세트 — 기대 발견 항목 목록을 두고, skill이 그 항목을 실제로 찾아내는지 자동으로 검증

## 일하는 방식에서 드러난 점

- **범위부터 자른다.** 이식도, 게이트도 "핵심 흐름이 먼저 돌게" 범위를 정하고 시작했다.
- **사람이 믿을 수 있는 구조를 만든다.** AI에게 더 많이 맡길수록 검증 게이트·평가 세트·차단 훅을 함께 만들었다.
- **결정을 기록한다.** 마이그레이션 이력, 결정 기록 문서로 다음 사람이 같은 판단을 반복하지 않게 했다.

## 이야기 포인트

- "AI를 개발에 어떻게 쓰나요?" → 개인 도구가 아니라 팀 워크플로로, 검증 게이트와 함께
- "두 도구(런타임)를 어떻게 맞췄나요?" → 기준을 하나로 두고 매핑 문서로 동기화, 1차 범위 제한
- "AI 결과물을 어떻게 믿나요?" → 시각 검증 게이트, 평가 세트로 skill 자체를 검증
